# data/stages

스테이지(`StageData`) 리소스(`*.tres`)를 이 폴더에 저작한다.
`StageDatabase`(autoload)가 시작 시 이 폴더의 모든 `.tres`를 로드해
`stage_id`로 조회를 제공한다.

- 정의 스키마: [`entities/stage/StageData.gd`](../../entities/stage/StageData.gd)
- 설계 정본: [`docs/combat-screen-design.md`](../../docs/combat-screen-design.md) §5

이 폴더가 비어 있어도 오류 없이 로드된다.

## 전체 구조 — 3챕터 x 3스테이지 (#408)

스테이지 규모는 **3챕터, 챕터당 3스테이지, 총 9스테이지**로 확정되어 있다.
**챕터 하나가 컨셉 하나를 갖는다.**

| 챕터 | 컨셉 | 맵 | 스테이지 | 저작 현황 |
|---|---|---|---|---|
| 1 | 육지 | `GrasslandMap` (초원) | 1-1, 1-2, 1-3 | 3/3 |
| 2 | 바다 | `BeachMap` (해변, #422) | 2-1, 2-2, 2-3 | 0/3 |
| 3 | 하늘 | `SkyIslandMap` (떠 있는 섬, #423) | 3-1, 3-2, 3-3 | 0/3 |

**세 컨셉 모두 맵이 있다.** 이제 어느 챕터를 저작해도 그 컨셉의 전장에서 열린다 —
컨셉->맵 대응의 출처는 `stage/StageMaps.gd`(#420)이고, 스테이지를 저작할 때
전장 코드를 건드릴 일은 없다.

컨셉은 `.tres` 에 저작하지 않는다 — `chapter` 에서 도출된다(아래 "컨셉은 따로 저작하지 않는다").

챕터에 속하지 않는 스테이지(테스트·연습)는 `chapter` 를 `StageData.NO_CHAPTER`(0)로 둔다.
기본값이 그 값이므로 **아무것도 적지 않으면 챕터 밖**이 된다.

## 저작된 스테이지

| 파일 | 챕터·번호 | 이름 | 편성 | 구성 |
|---|---|---|---|---|
| `stage_1_1.tres` | 1-1 | 1-1 시험장 | 강제(순혈 3인) | 시작 배치 3마리. 튜토리얼(#345) |
| `stage_1_2.tres` | 1-2 | 1-2 거점 | 자유 | **3페이즈 점령전**. 거점 존 하나 + 웨이브 3파(3/4/5마리, #435) |
| `stage_1_3.tres` | 1-3 | 1-3 우두머리의 자리 | 자유 | 보스 매머드 수인 단독(#376) |
| `stage_test.tres` | 챕터 밖 | 테스트 스테이지 | 자유 | 웨이브 4파 + 보스 여왕(#375) |

## 무엇을 저작하는가

지금 스키마에 있는 것은 설계 문서 §5 의 `[확정]` 사항뿐이다.

| 필드 | 내용 |
|---|---|
| `stage_id` | 고유 식별자 (예: `stage_1_1`) |
| `display_name` | 화면 표시 이름 |
| `chapter` | 속한 챕터 1..3. 비우면 챕터 밖(#408) |
| `number` | 챕터 안에서의 순번 1..3 (#408) |
| `description` | 설명 |
| `type` | 전투 / 점령 / 점령+전투 (§5.2) |
| `spawns` | 시작 시 **한 번에** 놓는 적 배치 |
| `waves` | 순서대로 나오는 적 무리 (#375) |
| `forced_party` | 플레이어 편성을 덮어쓸 파티 (비우면 자유 편성, #345) |
| `clear_rewards` | 클리어 보상. 키는 `CurrencySystem.DEFAULT_CURRENCIES` 의 재화 id |

## 웨이브 (#375)

`waves` 에 `StageWave` 를 순서대로 넣으면 **앞 웨이브를 전멸시켜야 다음이 놓인다.**
마지막 웨이브까지 전멸시켜야 소탕 완료다.

- 방아쇠는 **앞 웨이브 전멸** 하나뿐이다. 시간 기반 등장(N초 뒤)은 없다.
- `spawns` 와 `waves` 를 둘 다 채우면 `spawns` 를 먼저 놓고, 그것을 전멸시킨 뒤 웨이브가 시작된다.
  다만 **섞지 않는 편이 낫다** — 시작 배치가 화면에 번호 없는 '0파'처럼 보여
  플레이어가 세는 파 수와 저작된 수가 어긋난다. `stage_test.tres` 는 전부 웨이브에 넣었다.
- `is_boss` 는 **표시용**이다. 승리 조건을 바꾸지 않는다 — "마지막 웨이브 == 보스"로
  코드가 단정하면 보스 뒤에 잔당 웨이브를 붙이는 순간 깨진다.
- 웨이브가 놓일 때마다 `EventBus.stage_wave_started(stage_name, index, total, wave)` 가 뜬다.

## 승리 조건은 따로 저작하지 않는다

승리 조건 프리미티브(**소탕** / **점령**)는 `type`에서 **도출**된다.
`StageData.get_objectives()`가 §5.2 의 대응표를 그대로 구현한다.

| type | 승리 조건 |
|---|---|
| 전투 | 소탕 |
| 점령 | 점령 |
| 점령+전투 | 소탕 + 점령 |

둘을 각각 저작하게 두면 "전투인데 점령이 필요"처럼 서로 어긋나는 데이터가 만들어질 수 있다.
그래서 `type` 하나가 출처다.

## 아직 필드가 없는 것 (설계 `[미정]`)

임의의 기본값을 넣으면 나중에 밸런스를 정할 때 그 값이 근거처럼 남으므로 **만들지 않았다.**

- 존 확보 시간, 존 위치, 리스폰 규칙 (§5.2 `[미정]`)
- "점령+전투"에서 두 프리미티브를 순차/동시/보완 중 무엇으로 엮을지 (§5.2 `[미정]`)
- 잠입/전투 루트 선택 파라미터 (§7 `[미정]`)
- **시간차 스폰**(N초 뒤 등장) — 웨이브 방아쇠는 "앞 웨이브 전멸" 하나뿐이다
- 첫 클리어 보너스·별점·드랍 테이블

정해지면 `StageData.gd`의 "승리 조건" 절에 `@export` 필드를 **기본값과 함께** 추가한다.
기본값이 있으면 기존 `.tres`는 누락 필드를 기본값으로 로드하므로 호환이 유지된다.

## 게임플레이 연결

`stage/Stage1_1.gd`(`class_name Stage`)가 `StageSystem.get_current_stage()` 로 현재 정의를 읽어
파티·적을 놓고 승패를 판정한다. 출격 화면에서 다른 스테이지를 고르면
`StageSystem.stage_requested` 를 받아 그 배치로 방을 다시 만든다.

실제 스테이지 구성과 수치는 팀이 저작한다.

## 컨셉은 따로 저작하지 않는다 (#408)

컨셉(**육지** / **바다** / **하늘**)은 `chapter` 에서 **도출**된다.
`StageData.chapter_to_concept()` 가 대응표의 정본이다.

| chapter | 컨셉 |
|---|---|
| 1 | 육지 |
| 2 | 바다 |
| 3 | 하늘 |
| 0 (`NO_CHAPTER`) | 없음 (챕터 밖) |

승리 조건을 `type` 에서 도출한 것과 같은 이유다 — 둘을 각각 저작하게 두면
"2챕터인데 육지"처럼 서로 어긋나는 데이터가 만들어질 수 있다.

챕터 머리에 쓰는 문구도 `StageData.chapter_to_display_name()`(예: `"2챕터 · 바다"`)이 출처다.
화면은 이 대응을 다시 쓰지 않는다.

`stage_id` 에서 챕터 번호를 파싱하지 않는 이유: id 는 식별자일 뿐 형식을 약속한 적이 없다.
`stage_test` 처럼 챕터에 속하지 않는 id 가 이미 있고, 파싱은 그런 id 를 만나면 조용히
0 이나 엉뚱한 값을 내놓는다.

### 목록 순서

출격 화면은 `StageDatabase.get_ordered_ids()` 를 쓴다 — `(chapter, number)` 순으로 정렬되고
챕터 밖 스테이지가 맨 끝에 온다. `get_all_ids()` 는 Dictionary 키 순서라 파일 순회 순서에
달려 있으므로 목록 표시에는 쓰지 않는다.

- `get_authored_chapters()` — 스테이지가 하나라도 저작된 챕터만 돌려준다.
  저작 전인 챕터는 머리도 뜨지 않는다.
- `get_ids_by_chapter(chapter)` — 그 챕터의 스테이지, 번호 순.
- `get_chapterless_ids()` — 챕터 밖 스테이지.

### 여기에 없는 것

- **맵별 지형 효과**: 해변의 얕은 물은 **밟을 수 있는 바닥**이지 장애물이 아니다.
  물에서 이동이 느려지는 등의 규칙은 없다 — 전투 규칙이라 별도 판단이 필요하다.
- **하늘 맵의 낙하**: 없다. 섬 밖으로 **나가지 못한다**(#429) — 허공 칸에 충돌이 있어
  유닛이 섬 테두리에서 멈춘다. 파티·적 모두 같다.

  낙하·낙사를 만들지 않은 이유: 낙하를 넣으면 새 전투 규칙이 줄줄이 따라온다
  (낙하 피해량, 복귀 자리, 복귀 후 무적 시간, 넉백으로 밀어 떨어뜨리는 것이
  정당한 전술인지). 그 전부가 밸런스 결정이고, 하늘 맵 하나 때문에 전투 전체가
  달라진다. **막기만 하면 새 규칙이 하나도 생기지 않는다.**

  넉백(`EnemyBase.apply_knockback`)과 여왕 후퇴가 둘 다 `move_and_slide` 라서
  밀려나 떨어지는 일 자체가 없다.

  구현은 `SkyIslandMap._build_void_collision()` — 허공 칸을 가로로 병합해
  `VoidBlock` StaticBody2D 하나에 사각형 여러 개로 넣는다(실측 4127칸 -> 177형상).
  섬 둘레 한 칸만 막지 않는 이유는 그 함수 주석에 적었다.
- **해금 사슬**: 앞 스테이지를 깨야 다음이 열리는 규칙은 없다.
  `StageProgress` 는 클리어 횟수만 기록하고, 저작된 스테이지는 전부 고를 수 있다.
- **챕터 클리어 보상**: 보상 규칙은 스테이지별 `clear_rewards` 하나뿐이다.
