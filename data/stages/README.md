# data/stages

스테이지(`StageData`) 리소스(`*.tres`)를 이 폴더에 저작한다.
`StageDatabase`(autoload)가 시작 시 이 폴더의 모든 `.tres`를 로드해
`stage_id`로 조회를 제공한다.

- 정의 스키마: [`entities/stage/StageData.gd`](../../entities/stage/StageData.gd)
- 설계 정본: [`docs/combat-screen-design.md`](../../docs/combat-screen-design.md) §5

이 폴더가 비어 있어도 오류 없이 로드된다.

## 전체 구조 — 3챕터 x 3스테이지 (#408)

스테이지 규모는 **3챕터, 챕터당 3스테이지, 총 9스테이지**로 확정되어 있다.
**챕터 하나가 컨셉 하나를 갖는다.**

| 챕터 | 컨셉 | 맵 | 스테이지 | 저작 현황 |
|---|---|---|---|---|
| 1 | 육지 | `GrasslandMap` (초원) | 1-1, 1-2, 1-3 | 3/3 |
| 2 | 바다 | `BeachMap` (해변, #422) | 2-1, 2-2, 2-3 | 3/3 (#438, #566) |
| 3 | 하늘 | `SkyIslandMap` (떠 있는 섬, #423) | 3-1, 3-2, 3-3 | 3/3 (#567) |

**세 컨셉 모두 맵이 있다.** 이제 어느 챕터를 저작해도 그 컨셉의 전장에서 열린다 —
컨셉->맵 대응의 출처는 `stage/StageMaps.gd`(#420)이고, 스테이지를 저작할 때
전장 코드를 건드릴 일은 없다.

컨셉은 `.tres` 에 저작하지 않는다 — `chapter` 에서 도출된다(아래 "컨셉은 따로 저작하지 않는다").

챕터에 속하지 않는 스테이지(테스트·연습)는 `chapter` 를 `StageData.NO_CHAPTER`(0)로 둔다.
기본값이 그 값이므로 **아무것도 적지 않으면 챕터 밖**이 된다.

## 무엇을 저작하는가

지금 스키마에 있는 것은 설계 문서 §5 의 `[확정]` 사항뿐이다.

| 필드 | 내용 |
|---|---|
| `stage_id` | 고유 식별자 (예: `stage_1_1`) |
| `display_name` | 화면 표시 이름 |
| `chapter` | 속한 챕터 1..3. 비우면 챕터 밖(#408) |
| `number` | 챕터 안에서의 순번 1..3 (#408) |
| `description` | 개발 메모(저작 의도·밸런스 근거). **플레이어 화면에 띄우지 않는다** |
| `briefing` | 플레이어에게 보여 주는 작전 설명. 스테이지 리스트 팝업이 쓴다(#555) |
| `type` | 전투 / 점령 / 점령+전투 (§5.2) |
| `spawns` | 시작 시 **한 번에** 놓는 적 배치 |
| `waves` | 순서대로 나오는 적 무리 (#375). `requires_capture` 로 점령을 조건으로 걸 수 있다 (#442) |
| `forced_party` | 플레이어 편성을 덮어쓸 파티 (비우면 자유 편성, #345) |
| `clear_rewards` | 클리어 보상. 키는 `CurrencySystem.DEFAULT_CURRENCIES` 의 재화 id. 결과 화면 칩 수를 생각해 **스테이지당 재화 5종 이하**로 둔다 |
| `turn_level_bonus` | **턴제 전용.** 이 스테이지 적 전원의 레벨 보정 (기본 0, #565) |

## 웨이브 (#375)

`waves` 에 `StageWave` 를 순서대로 넣으면 **앞 웨이브를 전멸시켜야 다음이 놓인다.**
마지막 웨이브까지 전멸시켜야 소탕 완료다.

- 기본 방아쇠는 **앞 웨이브 전멸**이다. 여기에 `requires_capture`(#442)로 점령 조건을
  더 얹을 수 있다(아래). 시간 기반 등장(N초 뒤)은 없다.
- `spawns` 와 `waves` 를 둘 다 채우면 `spawns` 를 먼저 놓고, 그것을 전멸시킨 뒤 웨이브가 시작된다.
  다만 **섞지 않는 편이 낫다** — 시작 배치가 화면에 번호 없는 '0파'처럼 보여
  플레이어가 세는 파 수와 저작된 수가 어긋난다. `stage_test.tres` 는 전부 웨이브에 넣었다.
- `is_boss` 는 **표시용**이다. 승리 조건을 바꾸지 않는다 — "마지막 웨이브 == 보스"로
  코드가 단정하면 보스 뒤에 잔당 웨이브를 붙이는 순간 깨진다.
- 웨이브가 놓일 때마다 `EventBus.stage_wave_started(stage_name, index, total, wave)` 가 뜬다.

### 페이즈는 웨이브로 만든다

거점 존을 여러 개 두어 "페이즈"를 만들 수는 **없다.** 존은 시작 시 전부 활성화되고
`_all_zones_captured()` 가 **전부** 확보를 요구하므로, 파티가 한 곳씩 도는 동안 다른 곳이
`capture_decay_multiplier` 로 줄어든다 — 페이즈가 아니라 동시 다지점 방어가 된다.
존 활성화 순서 필드는 설계 §5.2 에서 `[미정]`이다.

웨이브만 "앞 무리 전멸"이라는 순차 방아쇠를 갖고 있다. 그래서 1-2(3페이즈)와
1-3(2페이즈)이 둘 다 웨이브로 페이즈를 표현한다.

### 점령을 웨이브 조건으로 걸 수 있다 (`requires_capture`, #442)

`StageWave.requires_capture = true` 인 웨이브는 **앞 무리 전멸 + 모든 존 확보** 둘 다
채워져야 놓인다. 기본값은 `false` 라 이 필드가 없는 기존 `.tres` 는 동작이 그대로다.

조건이 안 됐으면 그냥 **기다린다** — 전장에 적이 없고 점령 게이지만 차는 상태가 되며,
점령이 미완이라 `_objectives_met()` 가 false 이므로 승리로 끝나지도 않는다.

1-3 의 2파(보스)가 이것을 쓴다: **점을 확보해야 우두머리가 등장한다.**

`Stage._process()` 는 `_advance_wave_if_cleared()` 를 **먼저** 부르고 그다음 승리를
판정한다. 그래서 점령이 끝나는 프레임에 웨이브가 먼저 놓이고, 승리 판정은 "적이 있다"로
걸러진다 — 점령을 마치는 순간 승리해 버리는 일이 없다(실측: 확보와 보스 등장이 같은 프레임).

**저작 실수 둘은 `validate()` 가 막는다.** 둘 다 판이 영영 끝나지 않고 플레이어에게
원인이 안 보이는 교착 상태다:

- **점령을 요구하지 않는 `type`** 에서 켜는 것 — 존이 없으면 `_all_zones_captured()` 가
  항상 false 라 그 웨이브가 영원히 안 놓이고, 적이 없으니 소탕도 충족되지 않는다.
- **`spawns` 가 비었는데 `waves[0]` 에** 켜는 것 — 진입 시 `spawn_enemies()` 가
  `_advance_wave()` 를 **게이트를 거치지 않고** 직접 부르는 경로가 있다. 거기에 게이트를
  넣으면 적이 하나도 놓이지 않아 `_begin_judging()` 이 판정을 꺼 버린다. 그래서 게이트는
  **진행 경로(`_advance_wave_if_cleared`)에만** 두고, 이 조합 자체를 저작 시점에 막는다.
  (`spawns` 가 있으면 첫 웨이브 게이트는 정상이다.)

## 하늘 챕터 저작 규칙 (#567)

- **BOSS 등급은 3-3 2파에만 둔다.** `TurnBattle._boss_music()` 이 하늘 컨셉(`StageData.Concept.SKY`)의
  보스 웨이브에 최종 보스곡(`battle_final.ogg`)을 건다. 3-1 · 3-2 에 보스 등급 적이나 `is_boss` 웨이브를
  넣으면 최종곡이 미리 나온다. 3-3 1파와 3-1 · 3-2 는 하늘 전투곡(`battle_sky.ogg`)이다.
  (바다 챕터의 보스 웨이브는 일반 보스곡 `battle_boss.ogg` 다.)
- **점령 타입을 쓰지 않는다.** 턴제에는 점령 대응물이 없어(설계서 §18) 점령 스테이지는 턴제에서 원래 의도보다 쉬워진다.
  `type = BATTLE`, `spawns` 는 비우고 웨이브만 쓴다.
- **스폰 좌표는 섬 위여야 한다.** 하늘 본섬은 세계 좌표 중심 약 (348, 252), 반지름 약 (528, 312)px 의
  일그러진 타원이고, 섬 밖은 허공 충돌이다. 허공에 스폰되면 끼어서 움직이지 못한다. 테두리가 ±15% 흔들리므로
  **안쪽 80% 타원(반지름 약 440 × 260)** 안에 두고, 실시간으로 진입해 눈으로 확인한다.
- 하늘 챕터의 테마 적은 **익룡 수인**(#568)이다. 매머드 수인 · 서아 · 랩터 수인은 일부 웨이브에 남아 있다(편성 폭을 위해).
- **테마 적(수룡 · 익룡)은 아트가 아직 없다** — 도형 플레이스홀더로 선다. 그림이 들어와도 스테이지는 건드리지 않는다(적 정의만 바뀐다).

## 보상 — 챕터가 장비 티어를 연다 (#566)

장비 재료의 출처는 스테이지 보상뿐이다(상점은 비어 있다). 그래서 **챕터가 다음 장비 티어를 연다**:
1챕터 = 돌, 2챕터 = 철(철광석 · 석탄), 3챕터 = 후다만티움. 값은 전부 `[임시값]` 이다.
설계 근거와 챕터별 공급 계산은 [`docs/stage-expansion-design.md`](../../docs/stage-expansion-design.md) §3.

| 스테이지 | gold | protein | stone | iron_ore | coal | tin | copper | hudamantium |
|---|---|---|---|---|---|---|---|---|
| 1-3 | 180 | 200 | 110 | | 2 | | | |
| 2-1 | 110 | 120 | 70 | 4 | 1 | | | |
| 2-2 | 160 | 160 | | 6 | 2 | 6 | | |
| 2-3 | 280 | 280 | | 10 | 4 | | 6 | |
| 3-1 | 240 | 240 | | 3 | 3 | | | 4 |
| 3-2 | 320 | 320 | | 4 | 4 | | | 6 |
| 3-3 | 480 | 480 | | 6 | 6 | | | 10 |

- 철 4부위(ore 36 · coal 14 · gold 1040)는 2챕터 첫 클리어(ore 20 · coal 7 · gold 550) + 2-3 ×2 + 2-2 ×1 로 맞춘다.
- 후다만티움 4부위(huda 27 · coal 23 · gold 2260)는 3챕터 첫 클리어(huda 20 · coal 13 · gold 1040) + 3-2 ×2 + 3-1 ×2 로 맞춘다(#567).
- 새 챕터의 첫 스테이지는 **앞 챕터 보스보다 쉽고 덜 준다**(2-1 < 1-3, 3-1 < 2-3).
- 가정: 장비 1개를 여러 캐릭터가 동시에 착용할 수 있다(`EquipmentSystem.equip()` 이 다른 캐릭터의 착용을 확인하지 않는다).
- 결과 화면의 보상 줄은 `HFlowContainer` 라 칩이 7개(재화 5 + 「첫 클리어」 + 「삼각근 Lv.」)가 되어도 줄바꿈된다.

## 적 레벨 보정 (`turn_level_bonus`, #565)

```
턴제 적 레벨 = EnemyData.turn_level + StageData.turn_level_bonus   (기본 0)
```

같은 적 정의를 재사용하면서 뒤 챕터를 더 세게 만드는 수단이다. 적 정의를 레벨만 바꿔
복제하지 않는다 — 단일 출처가 깨지고 적 씬·아트까지 따라 늘어난다.

- **기본 0**: 이 필드가 없는 `.tres` 는 그대로 동작한다. 음수는 `validate()` 가 거부한다
  (적 레벨이 1 미만이 되는 저작 실수를 막는다. 쓰임새가 생기면 그때 푼다).
- **전원에게, 모든 웨이브에** 걸린다. 웨이브별·스폰별 보정은 없다.
- 레벨이 오르면 적 기준 곡선(`TurnCombatTuning.enemy_base_*`)이 그대로 적용된다 —
  Lv20 → Lv30 이면 HP ×2.4 · 공격 ×1.9 · 방어 ×1.6.
- 아군 레벨(파티 레벨)은 1파에서 가장 높은 적의 레벨이며 **보정이 포함된다.**
  보스 웨이브까지 따라 올라가지는 않는다(기존 규칙).
- `EnemyData.turn_*_override`(절대 지정)가 있는 적은 보정과 무관하게 그 값이다.
- **실시간 전투는 이 값을 읽지 않는다** (실시간에는 레벨 개념이 없다). 밸런스는 턴제 기준이다.

레벨 곡선의 설계값은 [`docs/stage-expansion-design.md`](../../docs/stage-expansion-design.md) 에 있다.

## 난이도 실측 (`VerifyStageDifficulty`, #565)

스테이지를 저작하거나 보정·보상을 바꾼 PR 은 **이 표를 본문에 붙인다.**

```bash
godot --headless --path . res://tests/stage/VerifyStageDifficulty.tscn
```

챕터에 속한 저작 스테이지 전부를 자동 전투로 잰다. 실제 전투처럼 1파로 시작하고 나머지는
`pending_waves`, `use_prep("energy")`, 사이클 제한 60, 시드 8개(고정). 점령 조건은 턴제에
대응물이 없어 전멸로 대체된다. 출력은 스테이지 × 프로필 × 파티별
`승 n/8 · 평균 사이클 · 평균 격파 · 남은 HP%` 이다(남은 HP% 는 패배를 0 으로 센 전 시행 평균).

**전력 프로필** — 챕터마다 플레이어가 갖고 있을 법한 성장 + 장비를 흉내 낸다
(무기는 도끼, 방어구 3부위).

| 프로필 | 삼각근 배수 | 장비 | 예상 구간 |
|---|---|---|---|
| P0 | ×1.0 | 없음 | 1챕터 |
| P1 | ×1.2 (Lv.5) | 돌 4부위 | 2챕터 |
| P2 | ×1.3 (Lv.7) | 철 4부위 | 3챕터 |
| P3 | ×1.35 (Lv.8) | 후다만티움 4부위 | 3챕터 반복 뒤 |

챕터 → 예상 프로필 대응(1→P0, 2→P1, 3→P2)은 `VerifyStageDifficulty.CHAPTER_PROFILE` 한 곳에 있다.

**파티**: **표준 파티(미나·하랑·설아·강지)가 판정**이다. 딜러 파티(미나·하랑·아린·태희)는
참고용이고 단언이 없다. 일반 스테이지는 힐러 파티에게 레벨 보정이 거의 안 먹고, 압박은
힐러 없는 파티에서 나온다 — 두 열을 같이 읽는다. **보스 스테이지**(보스 웨이브가 있는
스테이지)는 "다음 프로필"과 "성장 없이 장비만"(성장 배수 1.0 + 예상 프로필의 장비) 열도 찍는다.

**목표** (단언은 느슨하다 — 시드가 고정이라 흔들리지 않는다):

| 구분 | 예상 프로필(표준 파티) | 단언 |
|---|---|---|
| 일반 스테이지 | 8/8 승 | ✔ |
| 보스 스테이지 | 5/8 ~ 7/8 승, 남은 HP 35 ~ 70% | 5/8 이상만 ✔ |
| 보스 · 성장 없이 장비만 | 4/8 승 이하 (성장이 의미 있는지 확인) | 없음 |
| 전체 | 평균 사이클 30 이하 (교착 없음) | ✔ |

**읽을 때 주의**

- **8판은 표본이 작다.** 보스 스테이지의 읽기는 시드에 따라 한두 판 흔들린다
  (1-3 · P0 을 72시드로 재면 61%인데 8시드 블록은 3/8 ~ 8/8 로 나온다).
  시드를 고른 경위는 `SEEDS` 주석에 있다. 의심스러우면 시드를 늘려 확인한다.
- 이 하네스는 **원본 리소스를 건드리지 않고 세이브와 무관하다.** `CharacterDatabase` 캐릭터를
  복제한 사본에 성장 배수를 직접 넣고 장비를 끼운다. `PlayerProfile` 이 세이브에서 복원해
  원본에 넣어 둔 삼각근 Lv. 은 쓰지 않는다 — 안 그러면 실행하는 사람의 레벨에 따라 표가 달라진다.
- 사본의 성장이 **전투 유닛까지 가는 것은 #563(복제 때 `growth_multiplier` 소실) 이 고쳐진
  뒤**다. 그 전의 표는 P1 이상에서 성장분이 빠진 값(장비만)이다.
- 검증 씬은 종료할 때 **실제 세이브를 덮어쓴다**(`SaveSystem`). 실행 전에 백업한다.

## ⚠ 점령 존 + 보스를 함께 두면 수비 반경을 저작해야 한다

`EnemyBase._defend_anchor()` 는 씬에서 **가장 가까운 `CaptureZone`** 을 잡는다. 적과 존을
연결하는 필드가 없으므로 **그 스테이지의 모든 적**이, 보스까지 포함해 `defend_radius` 안으로
제한된다(`_clamp_to_defend_area()` 가 바깥 성분을 제거한다. `BossEnemyBase` 는 안무 중일 때만
`super._physics_process()` 를 건너뛴다).

공통값 `capture_defend_radius` 는 **320** 이다. 보스가 있는 스테이지에서 그대로 두면:

- 파티가 존에서 320px 밖으로 물러나면 **보스가 따라오지 못한다.** 원거리로 밖에서 때리는
  익스플로잇이 된다.
- 보스 대시는 클램프를 거치지 않으므로 쿨타임마다 한 번은 넘어오지만 그 사이에는 못 온다.

그래서 1-3 은 존에 **`defend_radius = 900`** 을 저작했다 — 보스 `detection_range`(800)보다
크므로 감지할 수 있는 거리 전부를 추격할 수 있다. 실측으로 보스가 존에서 394px 까지
나가 파티에 붙는 것을 확인했다(320 이었다면 그 자리에서 멈춘다).

**대가**: 같은 값이 그 스테이지의 잡몹에도 걸린다. 1-3 의 1파 수비 병력은 1-2(공통 320)보다
훨씬 넓게 파티를 따라온다. 존별 값이 하나뿐이라 페이즈마다 다르게 줄 수 없다.

적을 특정 존에 묶는 필드를 만들면 근본 해결이지만 스키마 변경이다.

## 승리 조건은 따로 저작하지 않는다

승리 조건 프리미티브(**소탕** / **점령**)는 `type`에서 **도출**된다.
`StageData.get_objectives()`가 §5.2 의 대응표를 그대로 구현한다.

| type | 승리 조건 |
|---|---|
| 전투 | 소탕 |
| 점령 | 점령 |
| 점령+전투 | 소탕 + 점령 |

둘을 각각 저작하게 두면 "전투인데 점령이 필요"처럼 서로 어긋나는 데이터가 만들어질 수 있다.
그래서 `type` 하나가 출처다.

## 아직 필드가 없는 것 (설계 `[미정]`)

임의의 기본값을 넣으면 나중에 밸런스를 정할 때 그 값이 근거처럼 남으므로 **만들지 않았다.**

- 존 확보 시간, 존 위치, 리스폰 규칙 (§5.2 `[미정]`)
- "점령+전투"에서 두 프리미티브를 순차/동시/보완 중 무엇으로 엮을지 (§5.2 `[미정]`)
- 잠입/전투 루트 선택 파라미터 (§7 `[미정]`)
- **시간차 스폰**(N초 뒤 등장) — 웨이브 방아쇠는 "앞 웨이브 전멸"과 점령(#442)뿐이다
- 첫 클리어 보너스·별점·드랍 테이블

정해지면 `StageData.gd`의 "승리 조건" 절에 `@export` 필드를 **기본값과 함께** 추가한다.
기본값이 있으면 기존 `.tres`는 누락 필드를 기본값으로 로드하므로 호환이 유지된다.

## 게임플레이 연결

`stage/Stage1_1.gd`(`class_name Stage`)가 `StageSystem.get_current_stage()` 로 현재 정의를 읽어
파티·적을 놓고 승패를 판정한다. 출격 화면에서 다른 스테이지를 고르면
`StageSystem.stage_requested` 를 받아 그 배치로 방을 다시 만든다.

실제 스테이지 구성과 수치는 팀이 저작한다.

## 컨셉은 따로 저작하지 않는다 (#408)

컨셉(**육지** / **바다** / **하늘**)은 `chapter` 에서 **도출**된다.
`StageData.chapter_to_concept()` 가 대응표의 정본이다.

| chapter | 컨셉 |
|---|---|
| 1 | 육지 |
| 2 | 바다 |
| 3 | 하늘 |
| 0 (`NO_CHAPTER`) | 없음 (챕터 밖) |

승리 조건을 `type` 에서 도출한 것과 같은 이유다 — 둘을 각각 저작하게 두면
"2챕터인데 육지"처럼 서로 어긋나는 데이터가 만들어질 수 있다.

챕터 머리에 쓰는 문구도 `StageData.chapter_to_display_name()`(예: `"2챕터 · 바다"`)이 출처다.
화면은 이 대응을 다시 쓰지 않는다.

`stage_id` 에서 챕터 번호를 파싱하지 않는 이유: id 는 식별자일 뿐 형식을 약속한 적이 없다.
`stage_test` 처럼 챕터에 속하지 않는 id 가 이미 있고, 파싱은 그런 id 를 만나면 조용히
0 이나 엉뚱한 값을 내놓는다.

### 목록 순서

출격 화면은 `StageDatabase.get_ordered_ids()` 를 쓴다 — `(chapter, number)` 순으로 정렬되고
챕터 밖 스테이지가 맨 끝에 온다. `get_all_ids()` 는 Dictionary 키 순서라 파일 순회 순서에
달려 있으므로 목록 표시에는 쓰지 않는다.

- `get_authored_chapters()` — 스테이지가 하나라도 저작된 챕터만 돌려준다.
  저작 전인 챕터는 머리도 뜨지 않는다.
- `get_ids_by_chapter(chapter)` — 그 챕터의 스테이지, 번호 순.
- `get_chapterless_ids()` — 챕터 밖 스테이지.

### 여기에 없는 것

- **맵별 지형 효과**: 해변의 얕은 물은 **밟을 수 있는 바닥**이지 장애물이 아니다.
  물에서 이동이 느려지는 등의 규칙은 없다 — 전투 규칙이라 별도 판단이 필요하다.
- **하늘 맵의 낙하**: 없다. 섬 밖으로 **나가지 못한다**(#429) — 허공 칸에 충돌이 있어
  유닛이 섬 테두리에서 멈춘다. 파티·적 모두 같다.

  낙하·낙사를 만들지 않은 이유: 낙하를 넣으면 새 전투 규칙이 줄줄이 따라온다
  (낙하 피해량, 복귀 자리, 복귀 후 무적 시간, 넉백으로 밀어 떨어뜨리는 것이
  정당한 전술인지). 그 전부가 밸런스 결정이고, 하늘 맵 하나 때문에 전투 전체가
  달라진다. **막기만 하면 새 규칙이 하나도 생기지 않는다.**

  넉백(`EnemyBase.apply_knockback`)과 여왕 후퇴가 둘 다 `move_and_slide` 라서
  밀려나 떨어지는 일 자체가 없다.

  구현은 `SkyIslandMap._build_void_collision()` — 허공 칸을 가로로 병합해
  `VoidBlock` StaticBody2D 하나에 사각형 여러 개로 넣는다(실측 4127칸 -> 177형상).
  섬 둘레 한 칸만 막지 않는 이유는 그 함수 주석에 적었다.
- **해금 사슬**: 앞 스테이지를 깨야 다음이 열리는 규칙은 없다.
  `StageProgress` 는 클리어 횟수만 기록하고, 저작된 스테이지는 전부 고를 수 있다.
- **챕터 클리어 보상**: 보상 규칙은 스테이지별 `clear_rewards` 하나뿐이다.
