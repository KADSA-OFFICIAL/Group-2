# data/stages

스테이지(`StageData`) 리소스(`*.tres`)를 이 폴더에 저작한다.
`StageDatabase`(autoload)가 시작 시 이 폴더의 모든 `.tres`를 로드해
`stage_id`로 조회를 제공한다.

- 정의 스키마: [`entities/stage/StageData.gd`](../../entities/stage/StageData.gd)
- 설계 정본: [`docs/combat-screen-design.md`](../../docs/combat-screen-design.md) §5

이 폴더가 비어 있어도 오류 없이 로드된다.

## 저작된 스테이지

| 파일 | 이름 | 편성 | 구성 |
|---|---|---|---|
| `stage_1_1.tres` | 1-1 시험장 | 강제(순혈 3인) | 시작 배치 3마리. 튜토리얼(#345) |
| `stage_test.tres` | 테스트 스테이지 | 자유 | 웨이브 4파 + 보스 여왕(#375) |

## 무엇을 저작하는가

지금 스키마에 있는 것은 설계 문서 §5 의 `[확정]` 사항뿐이다.

| 필드 | 내용 |
|---|---|
| `stage_id` | 고유 식별자 (예: `stage_1_1`) |
| `display_name` | 화면 표시 이름 |
| `description` | 설명 |
| `type` | 전투 / 점령 / 점령+전투 (§5.2) |
| `spawns` | 시작 시 **한 번에** 놓는 적 배치 |
| `waves` | 순서대로 나오는 적 무리 (#375) |
| `forced_party` | 플레이어 편성을 덮어쓸 파티 (비우면 자유 편성, #345) |
| `clear_rewards` | 클리어 보상. 키는 `CurrencySystem.DEFAULT_CURRENCIES` 의 재화 id |

## 웨이브 (#375)

`waves` 에 `StageWave` 를 순서대로 넣으면 **앞 웨이브를 전멸시켜야 다음이 놓인다.**
마지막 웨이브까지 전멸시켜야 소탕 완료다.

- 방아쇠는 **앞 웨이브 전멸** 하나뿐이다. 시간 기반 등장(N초 뒤)은 없다.
- `spawns` 와 `waves` 를 둘 다 채우면 `spawns` 를 먼저 놓고, 그것을 전멸시킨 뒤 웨이브가 시작된다.
  다만 **섞지 않는 편이 낫다** — 시작 배치가 화면에 번호 없는 '0파'처럼 보여
  플레이어가 세는 파 수와 저작된 수가 어긋난다. `stage_test.tres` 는 전부 웨이브에 넣었다.
- `is_boss` 는 **표시용**이다. 승리 조건을 바꾸지 않는다 — "마지막 웨이브 == 보스"로
  코드가 단정하면 보스 뒤에 잔당 웨이브를 붙이는 순간 깨진다.
- 웨이브가 놓일 때마다 `EventBus.stage_wave_started(stage_name, index, total, wave)` 가 뜬다.

## 승리 조건은 따로 저작하지 않는다

승리 조건 프리미티브(**소탕** / **점령**)는 `type`에서 **도출**된다.
`StageData.get_objectives()`가 §5.2 의 대응표를 그대로 구현한다.

| type | 승리 조건 |
|---|---|
| 전투 | 소탕 |
| 점령 | 점령 |
| 점령+전투 | 소탕 + 점령 |

둘을 각각 저작하게 두면 "전투인데 점령이 필요"처럼 서로 어긋나는 데이터가 만들어질 수 있다.
그래서 `type` 하나가 출처다.

## 아직 필드가 없는 것 (설계 `[미정]`)

임의의 기본값을 넣으면 나중에 밸런스를 정할 때 그 값이 근거처럼 남으므로 **만들지 않았다.**

- 존 확보 시간, 존 위치, 리스폰 규칙 (§5.2 `[미정]`)
- "점령+전투"에서 두 프리미티브를 순차/동시/보완 중 무엇으로 엮을지 (§5.2 `[미정]`)
- 잠입/전투 루트 선택 파라미터 (§7 `[미정]`)
- **시간차 스폰**(N초 뒤 등장) — 웨이브 방아쇠는 "앞 웨이브 전멸" 하나뿐이다
- 첫 클리어 보너스·별점·드랍 테이블

정해지면 `StageData.gd`의 "승리 조건" 절에 `@export` 필드를 **기본값과 함께** 추가한다.
기본값이 있으면 기존 `.tres`는 누락 필드를 기본값으로 로드하므로 호환이 유지된다.

## 게임플레이 연결

`stage/Stage1_1.gd`(`class_name Stage`)가 `StageSystem.get_current_stage()` 로 현재 정의를 읽어
파티·적을 놓고 승패를 판정한다. 출격 화면에서 다른 스테이지를 고르면
`StageSystem.stage_requested` 를 받아 그 배치로 방을 다시 만든다.

실제 스테이지 구성과 수치는 팀이 저작한다.
