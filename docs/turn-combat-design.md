# 턴제 전투 설계 정본 (Turn-Based Combat)

이 문서는 **구현된 턴제 전투의 정본**이다. 원본 기획서(「붕괴: 스타레일 전투 시스템 완전 해부
→ 2D 턴제 게임 설계서」, 코드네임 **PROJECT LUMEN**)에서 **확정한 값만** 추렸다.

기획서는 후보와 논의를 함께 담고 있어 "무엇이 실제로 구현되었는가"를 그것만 보고 알 수 없다.
여기서는 **지금 코드에 있는 것**과 **일부러 안 한 것**을 나눠 적는다.

- 관련 이슈: [#450](https://github.com/KADSA-OFFICIAL/Group-2/issues/450)
- 시스템 레지스트리: [SYSTEM_CONVENTIONS.md](../SYSTEM_CONVENTIONS.md) §1
- 실시간 전투 정본: [combat-screen-design.md](combat-screen-design.md) — **별개 축이며 계속 살아 있다**

---

## 0. 설계 3원칙

1. **모든 정보를 공개한다.** 적의 다음 행동, 예상 피해 수치, 타임라인 변화, 속도 구간.
   랜덤으로 지는 일이 없어야 한다.
2. **매 턴 작은 퍼즐이 생긴다.** "이번 턴에 무엇을 해야 하는가"가 항상 화면에 명시된다.
3. **성공은 폭발적으로 보상한다.** 격파 순간의 연출 밀도가 게임의 인상을 결정한다.

이 세 줄이 나머지 모든 결정의 근거다. 어떤 기능을 넣을지 말지 다툴 때 여기로 돌아온다.

## 1. 실시간 전투와의 관계

**턴제는 실시간 전투를 대체하지 않았다.** 두 전투가 나란히 존재한다.

| | 실시간 | 턴제 |
|---|---|---|
| 진입 | `main_realtime.tscn` (또는 `stage/Stage1_1.tscn` 단독) | **`main.tscn` ← 게임의 기본 진입** |
| 튜닝 | `CombatConfig` / `data/combat/combat_tuning.tres` | `TurnCombatConfig` / `data/combat/turn_combat_tuning.tres` |
| 스텟 | `PlayerStats` 실시간 파생 (`get_physical_attack()` 등) | `PlayerStats` 턴제 파생 (`get_speed()`, `get_crit_rate()` 등) |
| 스킬 | `CharacterData.skills` | `CharacterData.turn_skills` |
| 상태 효과 | `StatusEffectSystem` (초 단위) | `TurnStatusSystem` (턴 단위) |
| 상태 효과 정의 | `StatusEffectData` | `TurnStatus` (런타임) + `TurnSkillEffect` (저작) |

**공유하는 것**: `PlayerStats` · `CharacterData` · `CharacterDatabase` · `SkillData` ·
`EnemyData` · `EnemyDatabase` · `EquipmentSystem` · `CurrencySystem` · `EventBus`.
턴제는 이 시스템들을 **참조·확장**하며 같은 데이터를 다시 정의하지 않는다.

**나눈 것**: 튜닝 리소스 · 스킬 배열 · 상태 효과 지속시간 · EventBus 시그널 이름(`turn_` 접두어).
나눈 이유는 각 항목의 코드 주석에 적혀 있고, 요지는 "합치면 한쪽 밸런싱이 다른 쪽을 흔든다"다.

### 진입 경로 (#472)

`main.tscn` 이 **턴제 전투**를 연다. 실시간 전투는 `main_realtime.tscn` 으로 통째로 남아
있으므로 되돌리려면 그 씬을 실행하거나 `project.godot` 의 `run/main_scene` 을 바꾸면 된다.

```
main.tscn
 ├ TurnBattle             ← 턴제 전장 (stage/turn/TurnBattle.tscn)
 ├ MainScreenLauncher     ← 메인화면을 얹는다
 └ StageResultLauncher    ← 승패 시 결과 화면을 연다

main_realtime.tscn        ← 지금까지의 구성 (Stage1_1 + GameCamera + HUD + DebugOverlay)
```

출격 흐름은 **손대지 않았다.** 실시간 전장과 같은 규약을 쓴다:

```
스테이지 선택 → 편성 → 출격
  → StageSystem.request_stage(id)
  → stage_requested 신호
  → TurnBattle 이 그 스테이지로 전투를 다시 만든다
  → 마지막 웨이브 전멸 → EventBus.stage_completed → 결과 화면 + StageProgress
```

## 2. 모듈

```
TurnBattleManager       — 전체 흐름 상태 기계
 ├ TimelineSystem       — AV 계산, 행동 순서 큐, 앞당김/지연/추가 턴, 프리뷰
 ├ RankSystem           — 위치 관리, 밀치기/끌기, 사용·타격 판정, 어그로
 ├ TurnResourceSystem   — 공명 포인트, 오의 게이지, 열기
 ├ SkillResolver        — 스킬 실행, 대상 산출, 효과 적용, 특성 발동
 ├ DamagePipeline       — 버킷 순차 적용 (11단계)
 ├ ToughnessSystem      — 인성치, 자물쇠, 격파, 초격파
 ├ TurnStatusSystem     — 턴 단위 버프/디버프/DoT, 격파 상태이상 7종
 ├ TurnEnemyAI          — 행동 선택, 예고 생성, 자물쇠 생성, 자동 전투 정책
 ├ PresentationQueue    — 연출 큐 (로직과 완전 분리)
 └ EventBus             — 시스템 간 통신 (turn_* 시그널)
```

전부 `entities/combat/turn/` 아래 있고 **노드가 아니다**(`RefCounted`). 그래서 헤드리스에서
그대로 검증되고, 밸런스 시뮬레이터를 만들 때 씬을 띄우지 않아도 된다.

화면은 `stage/turn/TurnBattle.gd`(필드 + 연출 재생)와 `ui/turn/TurnBattleHUD.gd`(HUD)다.

## 3. 행동 순서

```
AV = 1000 / SPD
N사이클 종료 누적 AV = 15 + 10 x (N - 1)
```

AV가 가장 낮은 유닛이 행동하고, 행동 후 자기 AV를 리필한 뒤 그만큼을 전체에서 차감한다.
속도 200(AV 5)은 속도 100(AV 10)보다 정확히 2배 자주 행동한다.

### 속도 구간 (3사이클 = 35 AV 기준)

| SPD | 3사이클 내 행동 횟수 |
|---|---|
| 90 | 3회 |
| 100 | 3회 |
| 120 | 4회 |
| 143 | 5회 |
| 172 | 5회 |
| 200 | 7회 |

**구간은 UI에 명시한다.** `PlayerStats.get_speed_to_next_breakpoint()`가 "다음 구간까지 +N"을
돌려주고, 스텟 화면이 그것을 그대로 띄운다. 커뮤니티 계산기에 의존하게 만들지 않는다.

### 행동 조작과 가드레일

| 효과 | 정의 | 가드레일 |
|---|---|---|
| 앞당김 X% | 현재 AV를 `기준AV x X%` 감소 | **연속 적용 시 2회차부터 효율 50%씩 감쇠** |
| 지연 X% | 현재 AV를 `기준AV x X%` 증가 | 적은 효과 저항으로 일부 저항 |
| 추가 턴 | AV 소모 없이 즉시 1회 더 | **턴당 최대 2회 하드캡** |

앞당김 감쇠가 없으면 앞당김 100%를 서로 주고받아 무한 턴 루프가 성립한다.

### 타임라인 프리뷰 (FF10 식)

스킬에 커서를 올리면 `TimelineSystem.preview_if_acted()`가 "이 행동 후의 순서"를 돌려주고,
HUD가 반투명 고스트로 겹쳐 그린다. **HSR에도 없는 기능이며 이 설계의 차별화 지점이다.**

프리뷰는 상태를 바꾸지 않고, **실제 결과와 일치해야 한다** — 어긋나면 공개한 정보가 거짓말이
되어 기능의 값어치가 사라진다. 헤드리스 테스트가 프리뷰와 실제 순서를 직접 비교한다.

## 4. 랭크 (위치)

```
   [후열]                   [전열] │ [전열]                [후열]
  A4   A3   A2   A1          │       E1   E2   E3   E4   E5
```

아군 4랭크 / 적 5랭크. **1이 최전방이다.**

- 스킬마다 **사용 가능 랭크**와 **타격 가능 랭크**가 있고, UI는 8칸 점 아이콘(`○ ○ ● ●`)으로 그린다.
- 확산(Blast)은 3D 거리가 아니라 **배열 인덱스 ±1**로 판정한다.
- 밀치기 / 끌어당기기 / 자리바꿈 / 고정(이동 면역).

**핵심 루프**: 대형이 무너지면 스킬 사용 조건이 깨져 **약한 대체 행동만** 하게 된다.
즉 위치 조작 = 예방적 방어다. 적이 치유자를 A4에서 A1으로 끌어내면 힐을 못 쓰고 어그로가
폭증하며, 아군은 자리바꿈으로 대형을 복구해야 한다.

### 어그로

```
가중치 = 랭크계수 (A1:1.5 / A2:1.2 / A3:0.8 / A4:0.6)
       x 도발계수 (도발 시 999)
       x 저HP계수 (HP 30% 이하 시 1.3)
```

`RankSystem.aggro_probabilities()`가 각 아군의 대상 확률을 돌려주고, HUD가 옵션으로 노출한다.
완전 확정이면 퍼즐이 되고 완전 랜덤이면 억울해지므로 **가중치 랜덤**이며, 확률을 보여 준다.

## 5. 자원 4층

| 자원 | 소유 | 규칙 |
|---|---|---|
| **공명 포인트 (RP)** | 파티 공유 | 최대 5 / 초기 3 / 평타 +1 / 스킬 -1 |
| **오의 게이지** | 개인 | 평타 +20 · 스킬 +30 · 피격 +10 · 처치 +10 · 격파 +15 · 오의 후 +5 |
| **열기 (Heat)** | 파티 공유 | 냉각 0~40 / 최적 40~70 / 과열 70~100 |
| **준비 포인트** | 전투 전 | 3개. 오의 50% / 인성치 -50% / 보호막 / 선제 |

### 공명 포인트가 왜 중요한가

4명이 **하나의 지갑**을 쓴다. 그래서 RP를 먹는 캐릭터(딜러)와 버는 캐릭터(평타 힐러)라는
두 축이 생기고, 팀 조합이 자동으로 **경제 밸런싱 퍼즐**이 된다.

편성 화면은 `TurnResourceSystem.forecast_resonance_balance()`로 **사이클당 RP 수지**를 미리
계산해 경고한다 (`-0.7/사이클 → 위험 (공명 파산)`). 전투에 들어가 봐야 알게 되면 편성이 도박이 된다.

### 오의는 턴 밖에서 발동한다

**이 게임의 심장이다.** `TurnBattleManager.use_ultimate()`는 `phase`를 거의 보지 않는다.

- 적 큰 공격 직전에 보호막을 깔 수 있다
- 아군 턴 중간에 버프를 넣어 그 공격에 태울 수 있다
- 격파 직전에 넣어 타이밍을 조율할 수 있다

이 하나로 턴제가 "순서 기다리기"에서 **타이밍 게임**으로 승격된다.
가드레일: **한 유닛의 턴 사이에 최대 2개**(연쇄 오의 폭주 방지).

### 열기 (선택적 시스템)

| 구간 | 피해 | 받는 피해 |
|---|---|---|
| 냉각 (0~40) | -10% | — |
| 최적 (40~70) | +15% | -10% |
| 과열 (70~100) | -20% | +25% |

스킬 +8 / 오의 +15 / 평타 -5 / 턴 종료 -3. 매 사이클 **권장 행동**이 제시되고 수행하면 -10.

의도: 같은 스킬 반복 스팸을 시스템적으로 억제한다. 턴제 게임의 최대 고질병에 대한 해법이다.
**재미가 검증되지 않으면 `heat_enabled = false`로 끄면 되고, 나머지 시스템은 온전히 굴러간다.**

이 트레이드오프를 깨면 원소가 곧 티어표가 된다.

색맹 대응: 색만으로 구분하지 않고 **원소마다 고유 형태 문양**을 항상 병기한다.

| 타입 | 문양 | 인성치 배율 | 성질 |

| 참격 Slash | / | 1.0 | 균형형 |

## 7. 인성치 · 자물쇠 · 격파 ★ 핵심 발명

**약점 속성 공격만 인성치를 깎는다.** 비약점 공격은 HP만 깎는다.
속성은 데미지 배율이 아니라 **잠금 해제 키**다.

### 자물쇠 (Lock)

적이 행동을 예고할 때 그 행동에 맞는 **봉인 조건**이 함께 표시된다.

```
⚠ 다음 행동: 「멸절의 낙뢰」   예상 피해 1,240
🔒 봉인 조건:  🔨  ❄  ❄  ⚡      (강타 1 + 한기 2 + 전격 1)
▓▓▓▓▓▓▓░░░  인성치 84/140
```

1. 자물쇠 하나 해제 = **해당 타입 공격 1회 적중** (다단 히트는 여러 개를 연다)
2. 자물쇠 하나 해제 = **인성치도 함께 감소** (몫 = 최대 인성치 / 자물쇠 개수)
3. **전부 해제 → 행동 무산 + 즉시 격파**
4. **일부 해제 → 남은 비율만큼만 위력** (4개 중 3개 해제 = 위력 25%)
5. 적 행동이 끝나거나 무산되면 **다음 행동마다 다른 조합**으로 갱신

등급별 자물쇠 개수: 잡몹 1~2 / 정예 3~4 / 보스 4~6.

**자물쇠 타입은 약점 목록에서만 뽑는다.** 약점이 아닌 타입을 넣으면 그 칸이 인성치를 깎지
못한 채 열려 "자물쇠 해제 = 인성치 감소" 규칙이 깨지고, 자물쇠를 다 열어도 격파가 나지 않는다.
후보가 2종 이상이면 **최소 2종을 섞는다** — 한 종류로만 채우면 그 원소 캐릭터 하나가 매 턴
자물쇠를 혼자 다 열어 편성 퍼즐이 사라진다.

인성치 바는 **자물쇠 개수만큼 분절(segment)**로 그리고, 각 칸에 자물쇠 아이콘을 초소형으로
인라인 표시한다 — 자물쇠 조합을 상시 노출하면서 중앙 개방 원칙을 지키는 절충안이다.

### 격파 (Break)

인성치 0 도달 시:

1. 즉시 **격파 데미지** (원소 배율 적용)
2. 원소별 **상태이상** 부여
3. **적은 이번 턴 + 다음 턴 완전 행동 불가** (옥토패스식)
4. 격파 지속 중 **받는 피해 +25%, 방어력 -30%**
5. 격파 해제 시 **인성치 전량 회복**

```
격파 데미지 = 기준값(레벨) x 원소배율 x (0.5 + 최대인성치/40) x (1 + 격파특화)
              x 방어계수 x 저항계수 x 받는피해계수
```

보스는 **격파 저항**을 갖고 행동 불가 턴과 회복 속도가 줄어든다.
단, **최소 1턴은 보장된다** — 0턴이면 격파의 보상이 사라져 격파 축 자체가 죽는다.

인성치가 남아 있는 적은 받는 피해가 **10% 감소**한다. 즉 격파 자체가 곧 딜 증폭이다.

### 초격파 (Overbreak)

이미 격파된 적에게 넣은 인성치 피해가 `인성치 x 12`의 **별도 피해로 전환**된다.
"격파 특화" 스탯 하나만으로 굴러가는 딜링 축이며, 출시 시점엔 비주류로 두었다가 나중에
전용 서포터/장비를 추가해 **파워 인플레 없는 메타 전환 카드**로 쓴다.

## 8. 데미지 파이프라인

```
최종 데미지 =
    기본 데미지                    기본
  x (1 + Σ 피해증가)               버킷 A
  x (1 - 방어계수)                 버킷 B
  x (1 - 원소저항 + 저항관통)      버킷 C
  x (1 + Σ 받는피해증가)           버킷 D
  x 치명타 배율                    버킷 E
  x (1 + 격파보너스)               버킷 F
  x 열기 보정                      버킷 G
  x 랜덤 (0.97 ~ 1.03)

기본 데미지 = 스킬배율% x 기준스탯 + 고정값
방어계수   = DEF / (DEF + 150 + 8 x 공격자레벨)
```

11단계(`_step_base` → … → `_step_apply`)를 순서대로 실행하며 **각 단계가 계산 내역을 로그로
남긴다.** 그 로그가 그대로 플레이어용 전투 로그가 된다 — 디버깅과 유저 편의를 두 번 만들지 않는다.

### 왜 버킷을 쪼개는가

기본 데미지 10000에 +50% 버프 3개:

| | 결과 |
|---|---|
| 같은 버킷 3중첩 (공격력 +150%) | **25,000** |
| 서로 다른 버킷 분산 (공격력 / 피해증가 / 받는피해) | **33,750** |

**35% 차이.** 이것이 "왜 저 캐릭 셋을 같이 쓰면 시너지가 폭발하는가"의 수학적 정체다.
버프를 4~6개 버킷으로 쪼개 각 버킷을 다른 역할군이 담당하게 하면, 플레이어는 자연스럽게
"역할이 겹치지 않는 4명"을 조합하고 그게 곧 팀 빌딩의 재미가 된다.

**이 두 숫자는 헤드리스 테스트가 직접 검사한다.** 버킷이 가산으로 붕괴하면 전투는 정상으로
보이는 채로 팀 빌딩의 재미가 사라지므로, 눈으로는 잡을 수 없다.

### 버킷 담당 역할

| 버킷 | 효과 | 주 담당 |
|---|---|---|
| 기본 | 공격력% / 고정 공격력 | 조율자 |
| A | 피해증가%, 원소 피해 | 조율자 · 딜러 자체 |
| B | 방어력 감소 | 잠식자 |
| C | 저항 관통 | 잠식자 · 조율자 |
| D | 받는 피해 증가(취약) | 잠식자 |
| E | 치확 / 치피 | 조율자 · 장비 |
| F | 격파 특화 | 파괴자 · 격파형 조율자 |
| G | 열기 관리 | 전원 |

### 치명타가 나지 않는 피해

**지속 피해(DoT) · 추가 피해 · 격파 피해는 치명타가 나지 않는다.**
그래서 DoT 팀은 치명타 축(버킷 E)을 통째로 버리고 장비 요구사항이 완전히 달라진다 —
의도된 안티테제 설계다.

### 특성 발동 조건

특성(`ActionKind.TRAIT`)은 플레이어가 누르지 않고 조건부로 자동 발동한다.

| 조건 | 쓰는 곳 |
|---|---|
| `TURN_START` | 설아 「연산 보조」 — 2턴마다 공명 +1 |
| `ON_DAMAGE_TAKEN` | 미나 「반격의 잔불」 — **도발 상태에서만**, 턴당 2회 |

특성이 특성을 낳는 재귀는 막혀 있다 — 반격이 반격을 유발하면 두 탱커가 서로를 때린다.

## 12. 적

### 등급

| 등급 | HP 배수 | 공격력 배수 | 자물쇠 | 격파 저항 |
|---|---|---|---|---|
| 잡몹 | 1.0 | 1.0 | 1~2 | 0 |
| 정예 | 2.2 | 1.15 | 3~4 | 0 |
| 보스 | 7.0 | 1.4 | 4~6 | 30% |

### 왜 실시간 스텟을 그대로 쓰지 않는가 ★ 실제로 겪은 문제

실시간 적 HP는 **연속 DPS** 기준으로 잡혀 있다. 평타 쿨다운 0.5초면 1분에 120번 때리므로
HP를 수만으로 둬도 몇십 초에 끝난다. 턴제는 한 사이클에 파티 전체가 4~6번 행동할 뿐이라
**같은 HP가 수백 턴이 된다.** 자동 전투로 돌려 보니 보스가 76,800 HP에 파티 한 방이 100이어서
**768번**을 때려야 했다.

그래서 턴제 스텟은 **레벨과 등급에서 파생**한다(`TurnCombatTuning.enemy_base_*`).
개성은 `EnemyData.turn_*_multiplier`라는 별도 채널로 얹는다 — 실시간 `hp_multiplier`와
함께 곱하면 이중 계산이 되어, 매머드 보스가 실시간 x8 에 등급 x12 로 96배가 됐다.

기준값의 출처는 설계서 §4.15 표(Lv20 HP 1,800 / 공격 240 / 방어 320)이고, 표에 없는 레벨에서
값이 튀지 않게 지수 곡선으로 근사했다.

### 파티 레벨 ★ 실제로 겪은 문제

방어계수의 분모는 `150 + 8 x 공격자레벨`이다. 처음에 파티 레벨로
`PlayerProfile.deltoid_level`(1부터 시작하는 삼각근 Lv.)을 넣었더니 분모가 158이 되어
방어력 620인 보스에게 피해가 20%만 들어갔다.

**삼각근 Lv.은 성장 채널(기초 스텟 배수)이고 전투 레벨이 아니다.** 캐릭터 레벨 시스템은
아직 없으므로(Phase 2), `TurnBattleManager.start()`의 `party_level`이 0이면
**조우 레벨(가장 높은 적의 레벨)에 맞춘다.**

### 저작된 적

| 적 | 등급 | Lv | 약점 | 개성 (HP/공격/방어) |
|---|---|---|---|---|
| 벨로시랩터 수인 | 잡몹 | 20 | 한기 ❄ · 충격 ◇ · 참격 / | 0.55 / 0.80 / 0.60 |
| 벨로시랩터 수인 2 | 잡몹 | 20 | 전격 ⚡ · 관통 ↑ | 0.55 / 0.80 / 0.60 |
| 매머드 수인 | 정예 | 22 | 화염 ▲ · 광휘 ✦ · 강타 ■ | 1.40 / 1.10 / 1.40 |
| 서아 | 정예 | 22 | 침식 ⬢ · 한기 ❄ · 충격 ◇ · 참격 / | 1.0 / 1.0 / 1.0 |
| 매머드 수인 우두머리 | 보스 | 25 | 한기 ❄ · 화염 ▲ · 강타 ■ · 참격 / | 1.0 / 1.0 / 1.20 |
| 익룡 여왕 | 보스 | 25 | 전격 ⚡ · 광휘 ✦ · 관통 ↑ · 참격 / | 0.85 / 1.10 / 0.90 |

적 스킬은 `data/skills/turn/enemy/`에 **공용**으로 둔다. 원소와 물리 타입은 스킬이 아니라
**시전자**에게서 오므로(`SkillData.resolve_element()`), 같은 「돌진」이 벨로시랩터에게는
충격·참격, 매머드에게는 화염·강타로 나간다. 적을 늘릴 때마다 스킬을 복제하지 않는다.

구현된 보스 패턴: **대형 파괴형**(「낚아채기」로 후열을 끌어냄) · **디버프 압박형**
(「쇠약의 낙인」) · **전멸기**(「멸절의 낙뢰」 오의).

### 스테이지 → 턴제 조우 (#472)

실시간 전장은 `StageSpawn.enemy_scene`(PackedScene)을 좌표에 인스턴스한다. 턴제는 좌표가
없고 랭크만 있으므로 **정의(`EnemyData`)**가 필요하다. `TurnStageEncounter` 가 그 번역을 맡는다.

- 적 씬의 루트(`EnemyBase`)가 `data` 로 `EnemyData` 를 들고 있으므로 **그것을 읽는다.**
  씬 경로 → 적 id 매핑표를 만들지 않는다 — 두 곳을 고쳐야 하고, 한쪽을 빼먹으면
  **조용히 다른 적이 나온다.**
- `PackedScene.get_state()` 로 저장된 프로퍼티만 읽는다. **씬을 인스턴스하지 않는다.**
- `StageSpawn.count` 를 그대로 펼치고, 적 랭크 5개를 넘치는 분은 버린다.
- 웨이브가 저작되지 않은 스테이지는 `spawns` 전체를 한 웨이브로 본다.
- **적이 하나도 없는 웨이브는 버린다.** 남기면 전투가 즉시 "전멸"로 판정해 화면에는
  아무 일도 없이 웨이브 번호만 올라간다.

전부 `static` 이라 노드 없이 호출되고, 그래서 헤드리스에서 "저작된 스테이지 전부가 적이 있는
조우로 풀리는가"를 직접 검사할 수 있다.

실측 (`VerifyTurnStageBattle`):

| 스테이지 | 웨이브 | 적 |
|---|---|---|
| stage_1_1 (1-1 시험장) | 1 | 3체 |
| stage_1_2 (1-2 거점) | 3 | 12체 |
| stage_1_3 (1-3 우두머리의 자리) | 2 | 5체 |
| stage_2_1 (2-1 밀물 해안) | 1 | 4체 |
| stage_test | 4 | 10체 |

### 웨이브

한 무리를 전멸시키면 다음 무리가 등장하고, **아군의 HP·오의 게이지·상태이상은 그대로
이어진다** — 무리마다 회복시켜 주면 웨이브가 그냥 별개 전투 여러 개가 된다.

웨이브를 `TurnBattleManager` 가 소유하는 이유: `_check_end()` 가 "적이 없으면 승리"를
판정하는데 그 판단에 "남은 웨이브가 있는가"가 함께 들어가야 한다. 밖에서 콜백으로
끼워 넣으면 **승리 신호가 웨이브마다 나가 결과 화면이 여러 번 뜬다.**

새 웨이브의 적 `unit_id` 에는 웨이브 번호가 들어간다 — 같은 적이 웨이브마다 나오면 id 가
겹치고, 타임라인의 AV 딕셔너리가 앞 웨이브의 값을 그대로 쓴다.

### 적 정보 공개

```
⚠ 다음 행동: 「연쇄 화염탄」   예상 피해 840 x 3회
🔒 봉인:  ❄  ❄  🗡
```

예상 피해는 **아군의 현재 방어력·보호막·취약을 반영한 실제 예상치**다
(`SkillResolver.expected_damage()`가 파이프라인을 변동 없이 한 번 돌린다).
아군 스킬 툴팁도 **같은 함수**를 쓴다 — 두 곳이 다른 계산을 하면 공개한 수치를 신뢰할 수 없다.

난이도 옵션 `TurnCombatConfig.info_detail`: `VERBOSE`(수치 전부) / `STANDARD`(아이콘만) /
`CHALLENGE`(정보 최소). **기본은 VERBOSE** — 정보를 숨기는 쪽이 옵트인이어야 한다.

## 13. 사이클 제한 ★ 실제로 겪은 문제

`TurnBattleManager.cycle_limit`(0 = 제한 없음). 넘기면 패배한다.

파티에 힐러가 있고 적이 고HP 보스면 **양쪽이 서로를 죽이지 못하는 교착**이 생긴다.
자동 전투로 돌려 보니 수천 턴이 지나도 끝나지 않았고, 제한이 없으면 그것은 버그가 아니라
"아주 긴 전투"로 보여서 눈에 띄지 않는다.

설계서 §12의 엔드게임은 어차피 "사이클 제한 내 클리어"로 채점하므로, 제한은 이 시스템에
원래 있어야 하는 축이다. 스테이지가 값을 정한다.

## 14. UI 문법

핵심은 **"정보 패널을 만들지 않는다"**와 **"메타 화면과 같은 재질을 쓴다"** 둘이다.

| 원칙 | 내용 |
|---|---|
| 1. 중앙 개방 | 화면 중앙 60%에는 UI를 두지 않는다 |
| 2. 가장자리 흡착 | 모든 UI가 화면 4변에 붙는다. 여백은 메타 화면과 같은 14px |
| 3. 부품은 메타 화면 것 | `UITheme.overlay_*` 를 그대로 쓴다. 둥근 반투명 판(BG 34% + 테두리 1px) |
| 4. 팔레트도 메타 화면 것 | 색 값은 `UITheme` 팔레트에서만 온다. 전투 전용 팔레트를 따로 두지 않는다 |
| 5. 요소 종류 상한 6종 | 넘으면 새 요소를 만들지 말고 기존 요소에 흡수시킨다 |
| 6. 앰버 알약은 하나뿐 | 메인 화면의 "출격만 알약 배경을 가진다"와 같다. 전투에서는 행동 확정 버튼이 그 자리다 |
| 7. 라벨은 쓰되 아껴 쓴다 | 이름·구간명은 글자로 적는다. 다만 게이지에 "HP"·"SP" 를 붙이지는 않는다 — **색과 위치가 여전히 라벨**이다 |

#### 3·4·7번은 #478에서 정반대였다 (#489에서 뒤집혔다)

#478 은 이 화면을 **평행사변형(`skewX -12°`) + 막대 2종**으로만 그렸고, 어두운
네이비/시안 팔레트(`#0C111C` / `#4FE0E8`)에 **글자 라벨을 금지**했다. 그 규율 자체는
안에서 일관됐다. 문제는 바깥이었다 — **게임에 시각 언어가 두 개** 생겼다.

| | 메타 화면 | 전투 HUD (#478) |
|---|---|---|
| 형태 | 둥근 모서리 13/14/16/22 | 평행사변형 + 막대 |
| 팔레트 | 흙 톤 (`UITheme`) | 네이비/시안 (`TurnCombat`) |
| 아이콘 | 두들 PNG | 유니코드 문양 |
| 라벨 | 글자로 적는다 | 금지 |

출격 버튼을 누르면 미술이 통째로 바뀌고 돌아오면 다시 바뀌었다. 한 게임으로 읽히지
않아서, 화면 수가 많은 메타 쪽을 기준으로 모았다.

**바꾸지 않은 것**: 1·2·5번과 정보 구조, 전장 좌표. 두 화면은 애초에 같은 배치 원칙을
쓰고 있었다 — 가운데를 비우고 UI 를 4변에 붙인다. 실제로 달랐던 것은 표면 재질뿐이다.

#### 그림은 판 모양대로 자른다

#478 에서는 초상을 기울이면 얼굴이 전단되므로 **기울인 프레임 안에 축 정렬로** 세웠다.
지금은 판이 둥근 사각형이라 전단 문제가 없다. 대신 그림을 각지게 두면 카드 네 귀퉁이에서
그림이 판 밖으로 삐져나온다.

그래서 `_portrait_patch()` 가 **둥근 사각형 정점과 그에 맞는 UV** 를 만들어
`draw_colored_polygon` 에 넘긴다. 늘리지 않는 규칙은 그대로다 — 칸 비율과 같은 창을
UV 로 잘라 내고(가이드 §3.4), 세로 중심은 살짝 위에 둔다(정가운데로 자르면 턱이 먼저
잘려 나간다).

#### 5번의 6종

① 행동 순서 카드 ② 적 분절바+HP바 ③ 아군 초상+오의 ④ 아군 HP바+상태 점
⑤ 공명 핍 ⑥ 액션 버튼

필수 정보 7항목(§UI 규격) 중 **현재 웨이브는 좌상단 재화 칩형 알약**으로,
**배속·자동·일시정지는 우상단 원형 버튼**으로 둔다 — 둘 다 메인 화면 상단 바에 이미
있는 부품이라 새 요소로 세지 않는다. 열기 게이지는 ⑤ 와 한 판에 묶인다.

오의는 **별도 버튼이 없다.** 카드 아래 가는 게이지로 차고, 만충이면 그 자리가 앰버
배지로 바뀐다. 배지가 곧 버튼이다.

> **가장 중요한 교훈**: 정보를 담을 공간이 부족해 보여도 **중앙을 침범하지 마라.**
> 캐릭터가 주인공이고 UI는 액자다.

### 시각 언어

색 값의 출처는 **`UITheme` 팔레트 하나**다. `TurnCombat` 은 "어느 쓰임이 어느 색인가"만
정하고 hex 를 적지 않는다. 화면 코드는 둘 중 어느 쪽에서도 리터럴 hex 를 쓰지 않는다.

| 항목 | 값 | 출처 |
|---|---|---|
| 판 배경 | `BG` 34% | `TurnCombat.panel_fill()` |
| 판 외곽선 | `OUTLINE` 28%, 1px | `TurnCombat.panel_line()` |
| 모서리 | 카드 13 / 판 14 / 알약 22 | `UITheme.RADIUS*` |
| 아군 HP | `SAGE` | `COLOR_ALLY_HP` |
| 적 HP | `HOSTILE` | `COLOR_ENEMY_HP` |
| 인성치 | `CREAM` | `COLOR_TOUGHNESS` |
| 오의 준비·조준·주요 동작 | `AMBER` | `COLOR_ULT_READY` / `COLOR_AIM` |
| 활성 텍스트 | `CREAM` | `COLOR_TEXT_ACTIVE` |
| 비활성 텍스트·테두리 | `STONE_GRAY` / `OUTLINE` | `COLOR_TEXT_DIM` / `COLOR_BORDER_IDLE` |
| 빈 게이지 | `INK` 55% | `TurnCombat.gauge_empty()` |
| 장면 바닥 / 배경 | `INK` / `BG` | `COLOR_STAGE_FLOOR` / `COLOR_BACKDROP` |

#### 원소 7색만 이 팔레트 밖에 있다

#489 는 원소 7색도 흙 톤으로 내리려다 되돌렸다. **그 색은 UI 가 아니라 캐릭터 아트가
소유한다** — 전투 스프라이트의 원소 장식이 그 색으로 **그려져 있고**
(`art/battle-sprites/manifest.json` 의 `element_color`), 생성 도구는 그 색을 칠하는 것이
아니라 소스 아트에 이미 있는 것을 기록만 한다. 코드에서 값을 바꾸면 도구를 다시 돌려도
따라오지 않고, 스프라이트의 장식과 HUD 의 배지가 서로 다른 색이 된다.

`tests/combat/VerifyBattleSprites.gd:70` 이 그 어긋남을 잡는다. 바꾸려면 소스 플레이트를
다시 칠해야 하고, 그것은 별도 아트 작업이다.

원소색은 **분절 인성치 바와 원소 배지 전용**이다. 다른 요소에 쓰면 "칸 색 = 요구 속성"이
깨진다. 색맹 대응으로 문양(`ELEMENT_GLYPH`)을 **항상 함께** 둔다.

### UI 규격 (뷰포트 1280×720 기준)

| 영역 | 규격 |
|---|---|
| 상단 한 줄 | 웨이브 알약 높이 40 (좌측 여백 14) / 토글 32×32 간격 6, 우측 여백 14 |
| 좌측 행동 순서 | 카드 76×44 / 좌측 막대 6×32 / 초상 32×32 / 원소 배지 20 / 세로 간격 6 / 5개 유닛 |
| 적 정보 카드 | 카드 104×60 / 분절 칸 20×8 간격 4 / HP 바 84×7 / 상태 점 7 간격 4 |
| 하단 파티 | 초상 카드 68×84 테두리 3 / 카드 간격 78 / HP 바 68×6 (카드 아래 4px) / 오의 게이지 56×5, 만충 시 배지 68×18 |
| 공명·열기 | 판 236×76 / 핍 14 간격 6 / 열기 게이지 168×8 |
| 액션 | 확정 알약 200×54 (우하단) / 스킬 알약 200×44, 세로 간격 56 |

터치 히트박스는 **시각 크기와 분리한다.** 최소 56×56 으로 판정한다.
스킬 알약은 44 로 보이지만 세로 간격이 56 이라 판정이 겹치지 않는다.

**적 정보 카드 폭은 `ENEMY_SLOT_STEP`(112)보다 좁아야 한다.** 재디자인 초안에서 116 으로
뒀다가 적이 나란히 설 때 카드가 4px 겹쳤다. 같은 이유로 #478 의 클러스터가 100 이었다.
적 간격은 랭크 배치 = 전투 시스템의 소유이므로 UI 가 못 건드린다.

같은 이유로 **예상 피해 숫자는 카드 옆이 아니라 위에** 올린다. 카드 사이가 8px 뿐이라
옆에 두면 숫자가 이웃 카드의 HP 바를 덮는다.

#### 화면은 1280×720 이 아니다 — 절대 좌표를 쓰지 마라

프로젝트는 `canvas_items` + `expand` 스트레치를 쓴다. **창 비율이 16:9 가 아니면 캔버스가
기준 해상도보다 커진다.** 1920×1012 창의 실측 캔버스는 **1366×720** 이었다.

절대 좌표로 뒀을 때 실제로 나온 증상:

- 우하단 액션 버튼·스킬 스트립·우상단 토글이 오른쪽 끝에서 **114px 안쪽에 떠 있었다.**
  가장자리 흡착이 깨져 UI 가 화면 가운데로 흘러내린 것처럼 보였다.
- 전투 화면의 배경·지면 `ColorRect` 가 1280 폭이라 **오른쪽 86px 에 창 배경색 띠**가
  그대로 보였다.
- 중앙 충돌선과 격파 배너가 캔버스 중심이 아니라 x 636 / 360 에 그려져 왼쪽으로 치우쳤다.

규칙: **크기는 상수, 위치는 변 기준 여백**이다.

| 대상 | 기준 |
|---|---|
| 좌·상단 (타임라인, 웨이브 핍) | 절대 좌표 그대로 |
| 우·하단 (액션 버튼, 스킬 스트립, 토글, 파티 밴드, 공명·열기·예고) | `size` 에서 뺀 여백 |
| 전장 (적·아군 줄, 중앙선, 카메라, 배너) | 캔버스 **중심** 기준 |
| 배경·지면·플래시·컷인 판 | 캔버스 크기에 맞춘다 (`_fit_backdrop()`) |

`TurnBattle` 은 `get_viewport().size_changed` 에 붙어 `_fit_backdrop()` + `_sync_shapes()` 를
다시 돌린다. 도형 좌표는 HUD 가 캔버스 크기에서 계산하므로, 다시 놓지 않으면 UI 만
옮겨 가고 캐릭터는 제자리에 남는다.

#### 적 클러스터는 도형 정수리에서 46px 위다

`CLUSTER_GAP` 을 6 으로 뒀을 때 두 가지가 겹쳤다.

1. 클러스터가 적 도형 상단 27px 를 덮어 **적 HP 바가 적 도형 위에 얹혔다.** 둘 다
   `HOSTILE` 계열이라 빨강 위 빨강이 되어 남은 체력을 읽을 수 없었다.
2. 전투 화면이 원소 문양 라벨을 발밑 -112 에 놓고 그 글자가 22px 이므로 -112~-90 을
   쓴다. 6px 만 띄우면 클러스터 밑변(-84)이 그 문양과 겹쳤다.

정수리(-78)에서 46 이상 띄워야 둘 다 피한다. 대신 클러스터가 적에서 멀어지므로
**밑변에서 도형 정수리까지 1px 막대로 잇는다** — 5체가 나란히 서면 어느 바가 누구
것인지 위치만으로는 확신할 수 없다.

#### 분절 칸 폭은 고정한다

폭을 카드에 맞춰 나누면 자물쇠 1개짜리 적이 통짜 바로 보여 **"인성치가 가득하다"로
읽힌다.** 여기서 정보는 칸의 **개수**다. 칸이 넘쳐 폭을 넘길 때만 줄인다.

`TurnBattleHUD` 는 `_draw()` 로 직접 그린다. 매 프레임 바뀌는 게이지·핍·조준 표시
수십 개를 노드로 들고 있을 이유가 없고, 판은 `StyleBoxFlat` 을 `draw_style_box()` 로
그리므로 메타 화면의 `UITheme.overlay_*` 와 같은 모양이 나온다. 클릭 영역은 그리면서
히트존으로 등록한다.

### 구현된 컴포넌트

- **좌측 행동 순서 카드** — 5장, 좌측 막대 색이 아군/적 구분, 투명도 감쇠, CR 게이지,
  프리뷰 고스트, 카드 사이의 **사이클 경계선**, 추가 턴 막대. 지금 차례만 테두리가 크림
- **적 정보 카드** — 이름 / 분절 인성치 바 / HP 바 / 상태이상 색 점 / 예상 피해(카드 위)
- **아군 하단 밴드** — 편성 화면과 같은 초상 카드(68×84, 테두리 3, `muted(tint)` 면색),
  균일 간격 78, HP·보호막 게이지, 상태 점, 외곽선 넣은 이름.
  **카드 슬롯은 랭크가 정한다** (쓰러져도 밀리지 않는다)
- **공명 핍 + 열기** — 한 판에 묶는다. 핍 5개, 0개일 때 빈 칸이 경고색.
  열기는 최적 구간을 배경으로 표시한다
- **우하단 액션 + 스킬 알약** — 확정 버튼은 **화면에서 유일한 앰버 알약**이고
  아이콘 + 스킬 이름을 단다. 스킬 알약은 **그 자체가 버튼이다**(클릭 = 실행).
  **내 턴에만** 펼쳐지고, 아닐 때 확정 버튼은 "적 행동 중" 반투명 알약으로 내려간다
- **조준 표시** — 발밑 앰버 고리 + 적 카드 테두리 앰버 + `icon_mark` 배지.
  부수 대상에는 흐린 같은 고리
- **웨이브 알약 / 우상단 토글 3개** — 메인 화면 상단 바와 같은 부품.
  배속(핍 개수) / 자동(막대 점등) / 일시정지(막대 2개)

#### 일시정지는 실제로 멈춘다

처음에는 입력 분기가 `pass` 라 **눌러도 아무 일이 없었다.** 지금은 `pause_toggled` 로
전투 화면이 진행 루프와 연출 재생을 붙잡고, 그동안 **행동 입력도 닫는다** — 멈춘 척만
하고 클릭이 통하면 그것은 일시정지가 아니다. 히트존이 10개에서 3개(토글만)로 줄어든다.

`get_tree().paused` 를 쓰지 않는다. 그쪽은 트리 전체를 멈춰 HUD 의 `_process` 와 입력까지
죽이므로 **풀 수 없는 일시정지**가 된다(`ScreenManager` 가 메타 화면용으로 이미 그
스위치를 쓰고 있기도 하다). 멈추는 지점은 연출 한 조각이 끝난 **경계**다 — 트윈 도중에
끊으면 캐릭터가 어중간한 위치에 남고, 재개 시 그 트윈이 이미 끝나 연출이 한 칸 건너뛴다.

#### 2차 패널로 옮긴 정보

| 정보 | 어디로 |
|---|---|
| ~~스킬 목록~~ | ~~액션 버튼 호버 시 펼치는 패널~~ → **되돌렸다**, 아래 참조 |
| 적 행동 예고 **문장** | 조준 중인 적 1체에 한해 하단 밴드 우측 스트립. 요구 조건 자체는 분절 바가 항상 보여준다 |
| 현재 사이클 **숫자** | 타임라인 칩 사이의 경계 막대 (위치로) |
| 랭크 `A1` 표기 | 카드 슬롯 위치 (위치로) |
| `전투 불능` / `공명 파산` 글자 | 감광 + 빈 게이지색 / 핍 경고색 (색으로) |

#### "액션 입력 버튼 1개"는 지켜지지 않는다 (#478 후속)

스킬 목록을 액션 버튼 호버 시에만 펼쳤더니 **화면에 누를 수 있는 것이 하나도 보이지
않았다.** 무엇을 쓸 수 있는지 알려면 포인터를 92×66 버튼 위에 정확히 올려야 했고,
그 전까지는 조작 가능한 UI 가 없는 화면으로 읽혔다. 배속·자동·일시정지도 글자를 뺀
40×20 막대 토글이라 버튼으로 보이지 않는다.

지금은 **내 턴일 때만** 스킬 스트립을 펼쳐 둔다. 누를 수 있을 때만 보이므로 적 턴에는
여전히 버튼 1개이고, 클러터도 그 순간에만 생긴다. 스트립 클릭이 곧 실행이다 —
고르기와 확정을 나누면 두 번 눌러야 하고, 그 구조에서는 목록이 장식으로 보였다.

호버는 프리뷰만 담당하고, **고른 행동은 마우스가 떠나도 남는다.** 남지 않던 동안에는
스킬을 고르고 큰 버튼으로 손을 옮기는 순간 선택이 풀려서 항상 첫 행동만 확정됐다.

### 캐릭터 아트 적용 (#478 후속)

`docs`와 별개로 캐릭터 아트 에셋 가이드가 정한 다섯 용도 중, 저장소에 그림이 있는
것을 전투 화면에 붙였다.

| 용도 | 어디에 | 출처 |
|---|---|---|
| 초상 아이콘 (42×36) | 아군 하단 밴드 초상 프레임 | `PortraitSystem.get_portrait()` → `HUDKit.head_texture()` |
| 초상 아이콘 (칩용) | 좌측 타임라인 칩의 26px 패치. 아군·적 공통 | 위와 같음. 적은 `EnemyData.portrait` |
| 전신 일러스트 | 오의 컷인의 인물 | `HUDKit.trimmed_texture()` |
| 오의 컷인 | 좌측 40% 타이포 + 우측 인물 + 원소 조명 | `TurnBattle._play_cutin()` |
| 오의 엠블럼 | 컷인 타이포 뒤 워터마크 (208px) | `UITheme.role_emblem_path()` |

**어떤 그림을 쓸지는 `PortraitSystem`, 어떻게 자를지는 `HUDKit` 이 정한다.** 전투 화면이
`character.portrait` 를 직접 읽거나 크롭을 다시 계산하지 않는다 — 그러면 편성 화면에서
고른 초상과 전투·컷인의 그림이 어긋난다.

주의 두 가지:

- `HUDKit.head_texture()` 는 `AtlasTexture` 를 돌려준다. `draw_colored_polygon` 의 UV 는
  **아틀라스 원본 기준**이라 0~1 을 그대로 쓰면 잘라 둔 머리 영역이 무시되고 전신이
  들어온다(칩과 카드에 통짜 전신이 찍혔다). `region` 을 원본 좌표로 환산해야 한다.
- 초상을 칸 비율로 늘리지 않는다. 칸과 같은 비율의 창을 UV 로 잘라 낸다
  (아트 가이드 §3.4: "같은 파일을 늘려 쓰면 얼굴이 찌그러진다").

**원소 조명을 그림에 굽지 않는다** (아트 가이드 §4.2). 컷인의 원소색 조명은 코드가
합성하고, 그림은 중립 조명 투명 PNG 를 그대로 쓴다. 속성이 바뀌어도 다시 그릴 필요가 없다.

#### 전장의 유닛은 아직 네모다 — 슬롯은 열려 있다

전투 화면은 Phase 0 이라 유닛을 `tint` 색 `ColorRect` 로 세운다. `battle_sprite`
(`CharacterData` / `EnemyData`)가 비어 있을 때의 플레이스홀더다.

**`.tres` 에 텍스처만 넣으면 네모가 그림으로 바뀐다** — 스크립트를 고칠 필요가 없다.
칸은 아군 56×84(`ALLY_BODY`) / 적 62×78(`ENEMY_BODY`)이고 발밑이 노드 원점이며,
`STRETCH_KEEP_ASPECT_CENTERED` 라 늘어나지 않는다. 피격 명멸은 네모면 `color`,
그림이면 `modulate` 를 흔든다 — 그림의 `color` 를 흰색으로 만들면 그림이 사라진다.

저작 규약과 생성 프롬프트: [turn-battle-sprite-prompts.md](turn-battle-sprite-prompts.md)

**오의 전용 엠블럼 아트는 아직 없다.** 지금 있는 벡터는 역할 도형(`shape_tank` 사각형 /
`shape_ranged` 삼각형 / `shape_buffer` 마름모)뿐이고, "벡터 · 단색 실루엣 · 흰색"이라는
엠블럼 요구는 만족하므로 그것을 쓴다. 전용 아트가 들어오면 `UITheme.role_emblem_path()`
한 곳만 바꾼다.

## 15. 연출

로직은 즉시 계산을 끝내고, 연출은 `PresentationQueue`에 쌓아 순차 재생한다.
**그래서 배속이 공짜로 구현된다** — 재생 시간만 나누면 되고, 0으로 두면 연출이 사라져
헤드리스 테스트와 "연출 감소 모드"가 같은 경로를 쓴다.

### 타격 피드백 규격

| 요소 | 일반공격 | 스킬 | 오의 | 자물쇠 해제 | 약점 격파 |
|---|---|---|---|---|---|
| 히트스톱 | 2f | 4f | 8f | 3f | **12f** |
| 흔들림 진폭 | 2px | 5px | 12px | 3px | **20px** |
| 흔들림 지속 | 0.08s | 0.15s | 0.3s | 0.1s | **0.45s** |
| 슬로모션 | — | — | 0.1s @ 0.3x | — | **0.25s @ 0.15x** |
| 플래시 | — | 10% | 30% | 15% | **70%** |
| 넉백 | 4px | 10px | 24px | — | 32px |
| 파티클 | 8 | 25 | 80 | 15 | **150** |

무게 순서 **일반공격 < 스킬 < 오의 < 격파**가 뒤집히면 연출이 거짓말을 한다.
헤드리스 테스트가 이 순서를 검사한다.

### 데미지 숫자

| 종류 | 색 | 크기 | 애니메이션 |
|---|---|---|---|
| 일반 | `#FFFFFF` | 1.0x | 위로 튀며 페이드 |
| 치명타 | `#FFD54F` | **1.6x** | 스케일 팝(0→1.3→1.0) + `CRITICAL` |
| 약점 타격 | 원소색 | 1.2x | 원소 파티클 |
| 격파 | 원소색 + 백색 아웃라인 | **2.0x** | 대형 표시 |
| 지속 피해 | 상태이상색 | 0.8x | 작게 반복 |
| 회복 | `#66D9A6` | 1.0x | 부드럽게 상승 |

우선순위는 **격파 > 치명타 > 약점 > 지속 > 일반**. 격파 숫자가 치명타 스타일에 묻히면
격파의 존재감이 사라진다.

### 약점 격파 9단계 ★ 게임의 클라이맥스

```
1. 인성치 0 도달 감지
2. 전 게임 정지 (히트스톱 12프레임)
3. 인성치 바 방사형 파열 + 유리 파편 폭발
4. 시간 감속 (0.25초 @ 0.15배속)
5. 화면 전체 원소 색 플래시 (70% → 0%)
6. 원소별 전용 대형 이펙트
7. "BREAK!" 타이포그래피가 화면을 가로지름
8. 적 비틀거림 + 붉은 실루엣 명멸
9. 격파 데미지 대형 숫자 + 상태이상 아이콘 부착 + 전용 SFX
```

원소별 6단계 이펙트: 한기=결정 성장→균열→파쇄 / 화염=폭염+잔불 / 침식=중력 왜곡 /
전격=번개 분기+스트로브 / 광휘=방사형 광선+렌즈 플레어 / 풍압=진공 균열선 / 충격=충격파 링.

**단계 목록은 `PresentationQueue.break_steps()`가 데이터로 돌려주고 재생기는 재생만 한다** —
단계를 늘릴 때 재생기를 고치지 않아도 되고, 헤드리스에서 "9단계가 다 있는가"를 검사할 수 있다.

> Phase 0에서 격파 순간이 짜릿하지 않으면 전체 설계를 재검토하라.
> 아트를 입혀도 재미가 생기지 않는다.

### 오의 컷인 8단계 (3D 컷씬 대체)

암전(0.08s) → 스피드라인 → 일러스트 슬라이드 인 → **키네틱 타이포그래피** → 보이스 →
복귀 + 줌인 → 오의 모션 → 마무리 히트스톱.

**타이포그래피가 핵심이다.** 글자 자체가 연출이 되면 3D 카메라가 없어도 충분히 강렬하다
(페르소나 5 · 리버스: 1999가 증명).

### 자물쇠 해제음

**상승 음계로 설계한다.** 1개 = 도, 2개 = 미, 3개 = 솔, 전부 해제 = 한 옥타브 위.
`PresentationQueue.lock_pitch()`가 음정 배율을 돌려준다 — **연속 해제가 음악이 되게** 하려는 것이다.

## 17. 검증

```bash
# 브랜치를 옮긴 직후에는 반드시 먼저
godot --headless --path . --import

# 턴제 코어 (411개 검사, 헤드리스)
godot --headless --path . res://tests/combat/VerifyTurnCombat.tscn

# 스테이지 연동 (132개 검사, 헤드리스)
godot --headless --path . res://tests/combat/VerifyTurnStageBattle.tscn

# 회귀
godot --headless --path . res://tests/stage/VerifyStageMaps.tscn
godot --headless --path . res://tests/story/VerifyStoryChapters.tscn
```

`VerifyTurnCombat`이 검사하는 것 중 **눈으로는 잡을 수 없는 것들**:

- 설계서 §5.3의 25,000 vs 33,750 — 버킷이 가산으로 붕괴하면 전투는 정상으로 보인다
- 프리뷰와 실제 순서의 일치 — 어긋나면 공개한 정보가 거짓말이 된다
- 앞당김 연속 감쇠 · 추가 턴 하드캡 — 없으면 무한 루프가 성립한다
- 자물쇠 타입이 약점에서만 나오는지 — 아니면 자물쇠를 다 열어도 격파가 안 난다
- 격파 상태이상 7종이 서로 다른지 — 같으면 전략 선택이 사라진다
- 로스터의 원소가 어딘가에서 약점인지 — 아니면 그 캐릭터는 인성치를 못 깎는다
- 같은 시드의 전투 재현 — 리플레이·버그 재현의 전제
- **표준 조우 자동 전투 승률** — 자동 전투 정책이 회복 스킬을 빼먹는 회귀를 잡는다

`VerifyTurnStageBattle` 이 검사하는 것:

- 적 씬 6종 전부에서 `EnemyData` 를 꺼낼 수 있는지 — 못 꺼내면 그 웨이브가 조용히 비워진다
- 저작된 스테이지 전부가 **적이 있는** 웨이브로 풀리는지, 저작된 웨이브 수가 다 살아남는지
- 웨이브가 순서대로 알려지고, 중간 웨이브에서 승리 신호가 나가지 않는지
- 웨이브가 넘어갈 때 아군 HP·오의가 **이어지는지**
- 승패 신호가 **정확히 한 번** 나가는지 (여러 번이면 결과 화면이 겹친다)
- **`stage_started` 가 나가지 않는지** — 나가면 실시간 튜토리얼이 활성화되어 진행 불가로 멈춘다

수동 확인:

- `main.tscn` 실행 → 메인화면 → 출격 → 스테이지 → 턴제 전투 → 결과 화면
- 타임라인 프리뷰 · 자물쇠 해제 · 격파 9단계 · 배속 2x/3x
- `main_realtime.tscn` 실행 → 실시간 전투에 변화 없음

## 18. 일부러 안 한 것 (Non-goals)

| 항목 | 왜 | 언제 |
|---|---|---|
| 실시간 전투 삭제 | 파일은 그대로 남기고 진입만 옮겼다(#472). 되돌아갈 자리를 남긴다 | 별도 이슈 |

## 부록 — HSR과의 차이

| 요소 | HSR | 본 설계 |
|---|---|---|
| 위치 전술 | 사실상 없음 | **랭크 4/5 + 밀치기·끌기 + 스킬 위치 조건** |
| 약점 시스템 | 고정 약점 + 인성치 | **인성치 + 턴마다 갱신되는 자물쇠 조합** |
| 적 정보 | "큰 공격 예고" 정도 | **정확한 예상 피해 + 봉인 조건 전체 공개** |
| 격파 보상 | 행동 지연 25% | **완전 행동 불가 2턴 + 받는 피해 +25% + 방어 -30%** |
| 타임라인 프리뷰 | 없음 | **스킬 호버 시 순서 변화 미리보기** |
| 상성 축 | 원소 7 | **원소 7 x 물리 3 = 10축** |
| 반복 스팸 억제 | 없음 | **열기 게이지 + 매 사이클 권장 행동** |
| 추가 턴 활용 | 캐릭터 개별 | **배턴 양도 (누적 강화)** |
| 속도 구간 | 미표기 | **UI 명시** |
